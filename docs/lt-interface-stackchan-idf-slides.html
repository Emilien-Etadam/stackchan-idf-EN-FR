03stackchan-idf の対話応答

  • 機体が WebSocket で会話サーバーに直結
    • マイク音声を送り、返ってきた音声を再生・口パク
    • 接続先は OpenAI Realtime / Gemini Live / XiaoZhi から選択
  • 会話中に LLM が機体のツールを呼べる
    • 体: 表情・首振り・カタコト声
    • お手伝い: 時刻・状態・記憶・タイマー
    • ask_agent: 調べ物を家の Claude Code に頼む
これまでは OpenAI / Gemini のクラウド頼み → 今回、XiaoZhi で自宅のサーバーにつないだ
03 / 対話応答Interface オフ会 2026-10-16

04XiaoZhi (小智) — 自宅に立てられる会話サーバー

もとは中国の「小智」用
  • xiaozhi-esp32: 中国発のオープンソース AI 音声対話ファームウェア
    • ESP32 にマイクとスピーカーを付けて話しかける
  • 既定の接続先は公式クラウド (xiaozhi.me)
  • 機体とサーバーの間は公開された通信プロトコル
    • WebSocket + Opus 音声 + JSON、MCP でツール呼び出し
サーバーは自分で立てられる
  • 別プロジェクトの xiaozhi-esp32-server
    • Docker 構成と一発セットアップ用スクリプトが公開済み
    • 最小構成は 2 コア / 4 GB から (LLM は別)
  • VAD / 音声認識 / LLM / 音声合成を部品ごとに選べる
    • クラウド API でもローカルでも
stackchan-idf は XiaoZhi クライアントを実装済み → 接続先 URL を自宅サーバーにするだけ

07家の外から機体をつなぐ

課題
機体を持ち歩いても家のサーバーにつなぎたいポート開放はしたくない。ESP32 に重い仕組みは載せたくない
対策
Cloudflare Tunnel で WebSocket を 1 本だけ公開ホストの cloudflared が外向きに接続。TLS は Cloudflare 側
  • 認可は 2 段
    • ① Cloudflare Access: 機体が追加ヘッダーでサービス トークンを送る
    • ② XiaoZhi サーバー: Device-Id 許可リスト (知らない機体は即切断)
  • LLM・音声合成・管理用 HTTP は非公開のまま
ESP32 側の落とし穴
wss にすると TLS で内蔵 RAM が枯渇
(会話中の空き 11 KiB)
対策
Opus デコードを PSRAM にスタックを置いた専用タスクへ移動
WebSocket タスク 16 → 6 KiB
空き 11 → 27 KiB
LAN では直結も可
同じ設定項目で ws:// の LAN アドレスに切り替えるだけ

09ハマりどころ (ローカル LLM × XiaoZhi サーバー)

応答に \u30b9\u30bf… が混ざって読み上げられる
認識結果が JSON のまま LLM に渡り、Qwen が返事までエスケープ → 素のテキストで渡す
雑談中に突然「バイバイ」して切断
組み込みの退出判定ツールを誤発火 → 必須ツールから外す
ツールを呼んだ後から中国語で話し出す
ベース プロンプトが中国語 → 日本語に訳して差し替え
「さっきの物語の話だけど…」と蒸し返す
毎接続、few-shot 例の会話が履歴に入っていた → 短い挨拶に差し替え
速度: キャッシュを効かせる
2 回目の呼び出しでツール集合が変わるとプロンプト キャッシュが外れて 3〜5 秒 → 固定して 0.2〜1.8 秒
速度: 思考をオフ
会話に長考は要らない。最初のトークンまで 約 0.3 秒
デバッグ
サーバーと LLM の間に記録プロキシを挟み、実際のプロンプトを見るのが早い
