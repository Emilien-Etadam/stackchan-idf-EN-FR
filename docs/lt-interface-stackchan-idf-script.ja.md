## 0. タイトル (0:00–0:15)

stackchan-idf と Local LLM、ｽﾀｯｸﾁｬﾝの会話の頭を家のローカル LLM に載せ替えた話をします。

## 1. 自己紹介 (0:15–0:30)

井田です。組込みと FPGA をやっています。ESP-IDF で書いたｽﾀｯｸﾁｬﾝのファームウェア、stackchan-idf を作っています。

## 2. ｽﾀｯｸﾁｬﾝと stackchan-idf (0:30–1:00)

ｽﾀｯｸﾁｬﾝは、ししかわさんが作ったオープンソースの卓上ロボットです。M5Stack を頭にして、サーボ 2 個で首を振り、
画面の顔で表情を出します。ハードが公開されているので、ファームウェアもいろいろあります。

stackchan-idf はその 1 つで、私が ESP-IDF と C++ でゼロから書いています。ブラウザから書き込みと設定ができて、
AI との対話応答や、本体だけで動く音声合成などが入っています。今日はこの対話応答の話です。

## 3. stackchan-idf の対話応答 (1:00–1:30)

stackchan-idf の対話応答は、機体が WebSocket で会話サーバーに直接つなぎます。マイクの音声を送って、
返ってきた音声を再生して口を動かします。接続先は OpenAI Realtime、Gemini Live、XiaoZhi から選べます。

会話中には、LLM が機体のツールを呼べます。表情や首振りのような体の操作のほかに、時刻、記憶、タイマー、
それから調べ物を家の Claude Code に頼む ask_agent があります。今日の特集の言葉で言えば、小さなエージェントです。

ただ、これまではクラウドの会話 API 頼みでした。今回は XiaoZhi を使って、自宅のサーバーにつなぎました。

## 4. XiaoZhi (小智) とは (1:30–2:00)

XiaoZhi、小智は、もともと中国発のオープンソースの AI 音声対話ファームウェア xiaozhi-esp32 のための仕組みです。
ESP32 にマイクとスピーカーを付けて話しかけるもので、CoreS3 も対応ボードに入っています。既定では公式のクラウド xiaozhi.me につながります。
機体とサーバーの間の通信プロトコルが公開されていて、WebSocket に Opus の音声と JSON を流し、ツール呼び出しには MCP を使います。

プロトコルが公開されているので、サーバーは別プロジェクトの xiaozhi-esp32-server で自分で立てられます。
Docker の構成と、一発でセットアップするスクリプトが公開されています。VAD、音声認識、LLM、音声合成を
部品ごとに選べて、全部ローカルにもできます。

stackchan-idf は XiaoZhi のクライアントを実装済みなので、機体の側は接続先の URL を自宅のサーバーに変えるだけです。

## 5. 全体構成 (2:00–2:50)

全体はこうなっています。左がｽﾀｯｸﾁｬﾝ、真ん中が Cloudflare、右が自宅のホストです。

機体は wss で Cloudflare に発信するだけです。ホストの cloudflared が外向きにトンネルを張っているので、
家のルーターのポートは開けていません。TLS は Cloudflare で終わって、ホストには localhost の 8000 番で届きます。

ホストでは xiaozhi-esp32-server が、VAD、音声認識、LLM、音声合成の順に処理します。LLM は Strata で動かしている
Qwen3.8-Flash-Next の 125B、音声合成は VOICEVOX です。

ポイントは、音声と MCP が同じ WebSocket に乗っていることです。機体が MCP サーバーになっていて、
サーバー側の LLM が機体のツールを呼びます。特集の 4 章の栽培エージェントは、PC の MCP サーバーから
M5Stack の HTTP を叩く構成でしたが、こちらは向きが逆です。

## 6. ホスト側の部品 (2:50–3:15)

部品の一覧です。会話サーバーはフォークして日本語向けに直しています。音声認識は SenseVoice、LLM は
Strata で 125B を 2bit 量子化して、V100 1 枚に載せています。GPU は LLM で埋まりますが、音声合成は CPU の
VOICEVOX で足りています。GPU 1 枚と CPU という、そこそこの計算資源で会話の頭が丸ごとローカルで動く、というのがミソです。外に出るのは、ask_agent で Claude に頼むときだけです。

## 7. 家の外から機体をつなぐ (3:15–3:50)

家の外に機体を持ち出してもつながるように、Cloudflare Tunnel で WebSocket を 1 本だけ公開しています。
認可は 2 段です。Cloudflare Access のサービス トークンを機体が追加ヘッダーで送り、さらにサーバー側で
Device-Id の許可リストを見ます。LLM や音声合成のポートは公開していません。

ESP32 の側では、wss にすると TLS で内蔵 RAM が足りなくなりました。Opus のデコードを、PSRAM にスタックを
置いた専用タスクに移して、空きを 11 KiB から 27 KiB まで戻しています。

## 8. 1 ターンの流れ (3:50–4:25)

1 ターンの流れです。音声を送ると、サーバーが VAD と音声認識をして、LLM に発話とツール定義を渡します。
LLM が「表情を happy に」とツールを呼ぶと、サーバーが MCP の tools/call を機体に送って、機体が実行して
結果を返します。そのあと返答を文ごとに VOICEVOX で合成して、機体に音声で返します。

認識が終わってから最初の音声まで 1〜2 秒です。ツール呼び出しがあっても同じくらいです。

## 9. ハマりどころ (4:25–5:15)

ローカル LLM と XiaoZhi サーバーの組み合わせでハマったところです。

認識結果が JSON のまま渡っていて、Qwen が返事までエスケープしたので、`\u30b9` のようなエスケープ文字列を読み上げました。
雑談中に、組み込みの退出判定を誤って呼んで、突然バイバイと言って切れました。ベースのプロンプトが中国語なので、
ツールを呼んだ後から中国語で話し出しました。few-shot の例が毎回履歴に入っていて、物語の話を蒸し返しました。

速度では、ツール呼び出しの後でツールの集合が変わるとプロンプト キャッシュが外れて 3〜5 秒かかりました。
集合を固定して 0.2〜1.8 秒にしています。思考もオフにしました。
サーバーと LLM の間に記録プロキシを挟んで、実際のプロンプトを見るのが一番早かったです。

## 10. まとめ (5:15–5:35)

ｽﾀｯｸﾁｬﾝの会話の頭を、自宅のそこそこの計算資源で、全部ローカルに動かせました。家の外からは Cloudflare Tunnel と Access でつないでいます。
これから、割り込みと相槌を良くして、ask_agent の依頼先もローカルにしたいと思っています。ありがとうございました。
